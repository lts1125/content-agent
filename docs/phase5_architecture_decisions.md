## 1. 核心架构决策

### 1.1 为什么从"工具"升级为"Agent"

**背景**

项目最初是一个文案生成工具：用户打开 UI → 粘贴笔记 → 点击生成 → 拿到文案 → 关闭。每次调用无状态，历史生成风格、用户反馈、发布数据均未被活用。

**Agent 与工具的核心区别**

| 维度 | 工具 | Agent |
|------|------|-------|
| 触发 | 用户主动 | 自主感知环境，自主触发 |
| 决策 | 用户决定每一步 | Agent 自己规划路径 |
| 记忆 | 会话级/无状态 | 长期记忆，持续学习优化 |
| 目标 | 完成单次任务 | 追求一个长期目标 |
| 执行 | 用户点击后等待结果 | 定时/事件触发，循环执行 |

**决策**：将项目从"高级脚本"推进为"真 Agent"，实现自动感知外部热点、评估、选题、生成内容、入队发布的完整闭环。

**分支策略**：保留 `main` 分支为工具版，在 `agent-autonomy` 分支上实现 Agent 化升级。

---

### 1.2 为什么选择分层架构

**最终架构**

```
触发层    → CLI / APScheduler / Web UI
控制层    → AgentController / TrendScheduler
核心层    → Orchestrator (Writer → Editor 循环)
工具层    → content_agent/ (渲染、发布、检查)
数据层    → SQLite (publish_queue, topic_suggestions, style_samples)
```

**决策理由**

1. **触发层独立**：支持多种触发方式（定时、手动、事件），互不干扰
2. **控制层解耦**：AgentController 和 TrendScheduler 可以独立运行，也可以组合
3. **核心层复用**：Orchestrator 的写-编循环是通用能力，不绑定特定平台
4. **工具层可替换**：渲染器、发布器可以按需扩展（如新增抖音渲染器）

**替代方案**：单体脚本（所有逻辑在一个文件里）
- 拒绝理由：难以扩展，无法支持多平台、多触发源

---

### 1.3 为什么用 Python 而非其他语言

**决策**：继续使用 Python

**理由**
1. 已有代码库是 Python，迁移成本高
2. pydantic_ai 框架提供 Agent 抽象，生态成熟
3. 快速原型，迭代速度快
4. 团队熟悉度高

**缺点**
- 性能不如 Go/Rust（但本项目是 IO 密集型，非计算密集型）
- 部署体积大（但用 PyInstaller 打包为 .app 已解决）

## 2. Agent 化改造

### 2.1 为什么选择 ReAct 循环 + 状态机

**决策**：复用现有 Orchestrator 的 Writer → Editor 循环，扩展为 Agent 模式

**流程**

```
ResearchAgent → WriterAgent → EditorAgent (最多3轮)
```

**理由**
1. 已有实现，无需重写
2. 写-编循环天然适合内容生成场景
3. 3 轮限制防止无限循环和 token 爆炸

**替代方案**：LangChain / AutoGPT 等通用 Agent 框架
- 拒绝理由：过度设计，本项目场景单一（内容生成），不需要通用 Agent 的灵活性
- 通用框架引入过多抽象，调试困难

---

### 2.2 为什么 Agent 目标设定为"半自动"而非"全自动"

**决策**：保留人工 accept 作为把关，但 accept 后自动触发生成

**理由**
1. **内容安全**：AI 生成内容可能有幻觉、敏感信息，必须人工审核
2. **质量控制**：用户比 Agent 更懂自己的受众和调性
3. **平台风险**：自动发布可能导致账号封禁（尤其是小红书）
4. **渐进演进**：先半自动跑通流程，再逐步减少人工干预

**未来方向**：P2 阶段实现审核门（Gate），支持交互式确认、排期审核、跳过（开发调试用）

## 3. 热点监控体系

### 3.1 为什么需要外部热点感知

**背景**：原系统只能监听本地 Vault 文件变化，无法响应外部事件（如"微博热榜更新了"）

**决策**：新增 TrendWatcher 模块，支持多源热榜抓取

**理由**
1. 内容时效性：热点内容流量更高
2. 选题灵感：外部热点可以激发新的内容角度
3. 自动化：Agent 自主感知环境，无需用户手动输入

---

### 3.2 为什么选择 RSS 作为新闻源

**决策**：用 RSS 抓取实时科技新闻（36kr、机器之心、量子位、IT之家、TechCrunch、TheVerge、ArsTechnica）

**理由**
1. **标准化**：RSS 是通用格式，解析简单
2. **实时性**：新闻源更新频率高（分钟级）
3. **内容丰富**：有标题+摘要+链接，不只是标题
4. **无需 API Key**：公开 RSS 免费使用

**替代方案**
- **API 接口**（如 36kr API）：需要申请、有频率限制、可能收费
- **网页抓取**（爬虫）：需要维护选择器，容易失效
- **第三方聚合服务**（如 Feedly API）：依赖外部服务，不稳定

**RSS 的缺点**
- 部分源格式不规范（用正则宽松解析解决）
- 英文源需要翻译（用 LLM 翻译解决）

---

### 3.3 为什么热榜源和新闻源用不同的评估策略

**决策**
- **热榜源**（微博、知乎、掘金）：走 LLM 评估，判断技术深度和匹配度
- **新闻源**（RSS）：跳过 LLM 评估，直接生成选题

**理由**

| 维度 | 热榜源 | 新闻源 |
|------|--------|--------|
| 内容性质 | 话题讨论、技术文章 | 科技资讯、新闻报道 |
| 时效性 | 中等（小时级） | 高（分钟级） |
| 内容深度 | 深浅不一 | 较浅（资讯类） |
| 评估标准 | 是否值得深度解读 | 是否值得快速整理 |
| 生成形式 | 公众号长文（笔记驱动） | 抖音图文（热点驱动） |

新闻源的内容是资讯类，不需要技术深度评估，直接整理为抖音图文即可。热榜源的内容可能是技术文章，需要评估是否值得深入解读。

---

### 3.4 为什么新闻源要区分"突发热点"和"技术趋势"

**决策**：LLM 评估器 prompt 中区分两种评估标准

**背景**：早期评估器把掘金技术文章误判为"非热点"（得分 40-55），因为按"突发热点"标准评估（时效性、情绪强度）。

**修正**
- **突发热点**（微博）：时效性、情绪强度、传播潜力
- **技术趋势**（掘金/新闻源）：技术深度、实战价值、话题延展性、社区热度

**效果**：修复后技术趋势识别正常，置信度 70-85

## 4. 内容生成策略

### 4.1 为什么分"笔记驱动"和"热点驱动"两条线

**决策**：两条内容生成线并行

| 线 | 素材来源 | 目标平台 | 内容形式 |
|----|---------|---------|---------|
| 笔记驱动 | Vault 笔记 | 公众号、小红书 | 长文/短文 |
| 热点驱动 | 外部热点 | 抖音 | 图文卡片 |

**理由**
1. **平台差异**：公众号适合深度长文（基于笔记），抖音适合快速资讯（基于热点）
2. **内容差异**：笔记是用户积累的知识，热点是外部事件
3. **受众差异**：公众号受众是技术从业者（需要深度），抖音受众是泛科技用户（需要快速）

---

### 4.2 为什么抖音图文用 3 张卡片

**决策**：9:16 竖屏，3 张卡片（封面 + 核心看点 + 金句互动）

**演进过程**
- V1：7 张卡片（封面 + 5 张要点 + 金句 + 互动）→ 内容太少，每张只有 1-2 行
- V2：3 张卡片 → 信息密度高，用户滑动 3 次看完

**理由**
1. **信息密度**：第 2 张卡片合并所有要点（9-12 条），足够丰富
2. **用户体验**：3 次滑动完成阅读，不疲劳
3. **平台习惯**：抖音图文用户习惯快速滑动，不宜过多

**替代方案**：1 张长图
- 拒绝理由：内容过多，字体太小，阅读体验差

---

### 4.3 为什么抖音图文用 HTML 而非直接生成图片

**决策**：用 HTML + CSS 渲染，浏览器截图保存为图片

**理由**
1. **开发效率**：HTML/CSS 调试方便，改样式即时生效
2. **灵活性**：容易调整布局、颜色、字体
3. **可维护**：代码可读，后续修改简单

**缺点**
- 需要手动截图（暂未实现自动截图）
- 依赖浏览器渲染

**未来方向**：用 Playwright 自动截图（HTML → PNG）

---

### 4.4 为什么小红书用 4:3 卡片，抖音用 9:16

**决策**
- 小红书：900×1200（3:4）
- 抖音：1080×1920（9:16）

**理由**
1. **平台规范**：小红书推荐 3:4，抖音推荐 9:16
2. **用户习惯**：小红书用户习惯横滑浏览，抖音用户习惯竖滑
3. **内容密度**：9:16 更适合手机全屏展示

## 5. 多平台发布

### 5.1 为什么公众号用 kuaifa CLI

**决策**：用 `kuaifa` 命令行工具发布到微信公众号草稿箱

**理由**
1. **无需开发**：kuaifa 已封装微信 API，直接调用
2. **功能完整**：支持 Markdown 转公众号格式、上传封面、设置作者
3. **稳定可靠**：社区维护，持续更新

**缺点**
- 需要用户先登录 kuaifa（扫码授权）
- 不支持直接发布（只能到草稿箱，需手动确认）

**替代方案**：直接调用微信官方 API
- 拒绝理由：需要申请开发者资质、审核周期长、接口复杂

---

### 5.2 为什么小红书用半自动而非全自动

**决策**：半自动发布（生成发布指南 + 打开浏览器，用户手动粘贴）

**理由**
1. **无官方 API**：小红书未开放发布 API
2. **账号安全**：Playwright 模拟操作有封禁风险
3. **内容审核**：小红书审核严格，自动发布可能被拒
4. **实现简单**：不需要处理登录、验证码、Cookie 过期等复杂逻辑

**未来方向**：P3+ 升级为 Playwright 全自动（风险自负）

---

### 5.3 为什么抖音只生成图文 HTML，不自动发布

**决策**：生成 HTML 文件，用户手动截图上传

**理由**
1. **无发布 API**：抖音未开放图文发布 API
2. **封面图问题**：抖音图文需要封面图，自动生成质量难以保证
3. **审核机制**：抖音内容审核严格，自动发布风险高
4. **MVP 原则**：先跑通内容生成，发布后续优化

## 6. 数据与存储

### 6.1 为什么用 SQLite 而非 PostgreSQL/MySQL

**决策**：用 SQLite 作为持久化存储

**理由**
1. **轻量**：无需安装、配置、维护数据库服务
2. **单机**：本项目是单机应用，不需要多机共享数据
3. **简单**：Python 内置支持，无需额外依赖
4. **备份**：单个文件，容易备份和迁移

**缺点**
- 并发写入性能差（但本项目是单用户，无并发问题）
- 不适合大数据量（但内容数据量小，足够用）

**替代方案**：PostgreSQL
- 拒绝理由：过度设计，增加部署复杂度

---

### 6.2 为什么数据库表设计保持简单

**决策**：核心表只有 4 张（publish_queue, topic_suggestions, style_samples, content_metrics）

**理由**
1. **MVP 原则**：先跑通核心流程，再扩展
2. **避免过度设计**：不需要复杂的关联关系
3. **易于调试**：表结构简单，SQL 直观

## 7. 安全与审核

### 7.1 为什么必须加审核门（Gate）

**决策**：任何自动发布必须经过人工确认，默认不允许无人审核发布

**理由**
1. **内容安全**：AI 可能生成幻觉、敏感、违规内容
2. **账号安全**：自动发布可能导致平台封禁
3. **法律责任**：发布内容需由用户承担责任
4. **质量保证**：人工审核是最后一道防线

**审核门三种模式**
- **interactive**：终端交互确认（默认）
- **scheduled**：排期自动审核（已 approved 则自动通过）
- **disabled**：跳过审核（仅开发调试，打印警告）

---

### 7.2 为什么敏感词检查放在生成后

**决策**：内容生成后、入队前进行敏感词检查

**理由**
1. **拦截违规内容**：防止敏感内容进入发布队列
2. **提前发现**：在审核前就提示风险
3. **保护账号**：避免平台处罚

**检查时机**
```
生成内容 → 敏感词检查 → 入队 → 审核 → 发布
```
