# 公众号主链好用化设计文档

> 目标：下一阶段不继续扩平台，优先把“技术笔记 → 公众号可发布草稿”做成稳定、顺手、可持续使用的 Agent 主链。重点补齐历史任务、上下文续写、引用透明和偏好学习落地。

---

## 一、定位判断

当前项目已经不是单纯的 AI 写作脚本，而是一个“Agent 化的内容生产 MVP”：

- 用户可以输入主题或上传笔记
- 系统可以生成公众号、小红书、抖音等平台内容
- 公众号内容可以保存为 Markdown，并进一步保存到微信公众号草稿箱
- 已有进度提示、审核面板、下载按钮、RAG 检索、简单记忆和 session 展示

但从产品体验看，它还没有完全达到“每天愿意用”的内容工作台。核心差距不是模型能力，而是以下几类连续使用问题：

| 维度 | 当前状态 | 主要差距 |
|------|----------|----------|
| 历史任务 | 有 SQLite task/session 数据，有 `#!sessions` 命令 | 普通用户不能直观看到历史内容、评分、文件、发布状态 |
| 上下文续写 | 会保存会话轮次 | 生成时尚未系统使用最近对话理解“刚才那篇”“继续改” |
| 引用透明 | 生成时会注入相关笔记 | 用户看不到本次用了哪些笔记，也不能排除误召回 |
| 偏好学习 | 有 `PreferenceLearner` 和 `user_preferences` | 学到的偏好尚未充分影响公众号生成策略 |
| 发布闭环 | 可保存公众号草稿箱 | 缺少发布前状态、失败恢复、草稿记录和再次发布入口 |

下一阶段建议把产品定位收敛为：

> 一个帮助个人技术创作者把学习笔记稳定转成微信公众号草稿的 AI 内容 Agent。

### 阶段进度（截至 2026-06-01）

| 模块 | 状态 | 已完成内容 |
|------|------|------------|
| 历史任务中心 | 部分完成 | 页面展示最近生成历史，卡片化显示 task、文件、续改命令和发布状态 |
| 上下文续写 | 已完成第一版 | 支持“把刚才那篇继续改”和按 `task_id` 指定历史公众号文章 |
| 引用透明 | 已完成第一版 | 生成结果展示本次参考的历史笔记；未命中时明确说明 |
| 上传笔记去重 | 已完成第一版 | 上传笔记按内容 hash 去重，重复上传跳过向量库写入 |
| 发布闭环 | 部分完成 | 保存公众号草稿箱成功/失败后回写历史任务发布状态 |
| 公众号偏好落地 | 部分完成 | 已将公众号专属偏好、长度偏好和弱项提醒映射为生成约束，左侧展示当前真实偏好，并在结果中展示本次应用偏好 |

## 二、设计原则

1. **主链优先**  
   优先服务“上传/选择笔记 → 生成公众号文章 → 审核修改 → 保存草稿箱”这条链路，其他平台能力保持可用但不继续扩展。

2. **可见可控**  
   Agent 做了什么、参考了什么、为什么这么写，都要尽量让用户看见。尤其是 RAG 和记忆，不能只在后台悄悄影响结果。

3. **失败可恢复**  
   搜索、RAG、发布、模型调用都可能失败。失败时不应让用户从头再来，而是保留已生成内容、文件路径和下一步建议。

4. **记忆先保守后智能**  
   先做明确、可解释、可撤销的记忆，比如历史任务、用户明确偏好、引用笔记。后续再做自动学习和自动推断。

5. **少打扰用户**  
   Agent 可以主动给计划和建议，但不要每一步都要求确认。只在写作方向、引用素材、发布草稿箱这类关键节点提供确认或修改入口。

## 三、目标范围

### 3.1 本阶段要做

本阶段建议拆成四个功能块：

1. **历史任务中心**
   - 展示最近生成任务
   - 支持查看公众号文章、评分、文件路径、发布状态
   - 支持恢复到聊天窗口继续修改

2. **上下文续写**
   - 让用户可以自然说“把刚才那篇改得更通俗一点”
   - 生成前读取最近会话和最近任务
   - 自动识别“上一版文章”并作为修改素材

3. **引用透明**
   - 展示本次 RAG 命中的笔记
   - 在生成结果里显示“本次参考资料”
   - 后续支持用户排除某条引用

4. **公众号偏好落地**
   - 将偏好学习结果转换成公众号写作约束
   - 支持用户显式设置公众号默认读者和风格
   - 生成时优先使用公众号偏好，而不是泛平台偏好

### 3.2 本阶段不做

- 不新增新的内容平台
- 不做完全自动发布
- 不做多人协作和多用户权限
- 不做复杂 CRM 或内容数据大盘
- 不强依赖在线搜索，搜索失败时仍然以本地笔记生成

## 四、用户主流程

### 4.1 从笔记生成公众号草稿

```text
上传/粘贴技术笔记
  ↓
Agent 分析目标：公众号文章
  ↓
展示执行计划：
  - 使用上传笔记
  - 检索相关历史笔记
  - 生成通俗/技术风格公众号文章
  - 质量审核
  - 保存 Markdown
  ↓
生成文章
  ↓
展示审核结果和引用来源
  ↓
用户选择：
  - 继续修改
  - 下载 Markdown
  - 上传封面并保存到公众号草稿箱
```

### 4.2 基于上一版继续修改

```text
用户：把刚才那篇改得更通俗一点
  ↓
系统识别：
  - 指代对象：最近一次公众号生成结果
  - 修改要求：通俗、少术语
  ↓
读取最近任务的公众号 Markdown
  ↓
重新生成或定向修改
  ↓
保存为新版本
```

### 4.3 从历史任务恢复

```text
用户打开历史任务中心
  ↓
选择一条任务
  ↓
查看：标题、平台、评分、文件、引用、发布状态
  ↓
点击：
  - 继续修改
  - 重新生成
  - 发布到公众号草稿箱
```

## 五、功能设计

## 5.1 历史任务中心

### 当前基础

当前 `agents/store.py` 已有：

- `tasks`
- `drafts`
- `edit_history`
- `review_panels`
- `conversation_turns`

这些已经足够支撑第一版历史任务中心，不需要重新建一套存储。

### UI 形态

建议在 `chat_ui.py` 里新增一个折叠区域或 Tab：

```text
📚 历史任务

| 时间 | 标题/主题 | 平台 | 评分 | 状态 | 操作 |
|------|-----------|------|------|------|------|
| 05-31 10:20 | AI 工具为什么不好用 | 公众号 | 88 | 已保存文件 | 查看 / 继续改 / 发布 |
```

第一版可以简单一些：

- 默认显示最近 10 条
- 只显示公众号相关任务
- 点击“查看”把内容追加到聊天区
- 点击“继续改”把上一版内容带入输入框

### 数据要求

历史任务至少要展示：

| 字段 | 来源 | 说明 |
|------|------|------|
| `task_id` | `tasks.task_id` | 任务唯一 ID |
| `created_at` | `tasks.created_at` | 生成时间 |
| `title` | 从公众号 Markdown 第一行提取，或 metadata | 历史列表主标题 |
| `platforms` | `metadata` 或 assistant turn | 生成平台 |
| `score` | `edit_history.overall` 或 review panel | 质量评分 |
| `files` | `conversation_turns.files` 或新建 task_files | 下载/恢复路径 |
| `publish_status` | publish queue 或 metadata | 是否保存草稿箱 |

### 建议补充

当前 `conversation_turns.files` 可以记录文件，但任务和文件关系不够稳定。建议新增轻量表：

```sql
CREATE TABLE IF NOT EXISTS task_files (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id TEXT NOT NULL,
    platform TEXT NOT NULL,
    file_path TEXT NOT NULL,
    file_type TEXT NOT NULL DEFAULT 'markdown',
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

如果暂时不想加表，也可以第一版继续复用 `conversation_turns.files`，后续再迁移。

## 5.2 上下文续写

### 当前基础

当前 `MemoryManager` 已有：

- `save_turn()`
- `get_recent_turns()`
- `get_session_summary()`

但 `chat_ui.py` 生成时主要使用用户当前消息，尚未把最近会话系统性注入任务理解阶段。

### 目标能力

用户可以自然输入：

```text
把刚才那篇改得更通俗一点
```

```text
上一版太像技术文档了，改成普通人也能看懂的公众号文章
```

```text
保留结构，但是开头更抓人一点
```

系统应该能识别：

- 这是修改请求，不是全新生成
- 修改对象是最近一次公众号结果
- 修改要求是风格、结构、开头、长度等

### 设计方式

新增一个轻量的 `ConversationResolver`，负责把用户当前消息解析成上下文动作：

```python
class ConversationResolver:
    def resolve(self, message: str, session_id: str) -> ResolvedIntent:
        """
        返回：
        - action: generate_new | revise_previous | inspect_history
        - target_task_id: 如果是修改历史任务
        - target_platform: 默认 gongzhonghao
        - source_content: 上一版公众号内容
        - revision_instruction: 修改要求
        """
```

第一版不需要 LLM，可用规则识别：

| 触发词 | action |
|--------|--------|
| 刚才那篇、上一版、上面这篇、这篇文章 | `revise_previous` |
| 改得、更、优化、调整、重写、保留结构 | `revise_previous` |
| 写一篇、生成一篇、根据这篇笔记 | `generate_new` |

### 生成输入拼接

如果识别为 `revise_previous`，生成输入应变成：

```text
【上一版公众号文章】
...

【修改要求】
把它改得更通俗一点，少用术语，多举例子。

【输出要求】
只输出修改后的微信公众号文章。
```

这样比直接把聊天历史塞进 prompt 更稳定。

### 失败兜底

如果用户说“刚才那篇”，但找不到上一版公众号内容：

```text
我没有找到上一版公众号文章。你可以重新上传笔记，或者从历史任务里选择一篇继续修改。
```

## 5.3 引用透明

### 当前基础

当前 `_build_memory_context()` 会检索相关笔记：

```python
notes = self.memory.search_notes(topic, top_k=3, min_score=0.4)
```

但这些结果只被拼进 prompt，用户看不到。

### 目标体验

生成完成后，在结果里增加：

```text
📚 本次参考了 3 条历史笔记

1. Content Agent 起源笔记 / 三、从理论到实践
2. 微信公众号草稿箱发布功能实现笔记 / 发布流程
3. Docker 部署记录 / 依赖瘦身
```

如果 RAG 不可用：

```text
📚 本次未使用历史笔记，仅基于当前输入生成。
```

### 数据结构

建议在单次生成中保存 `memory_refs`：

```python
memory_refs = [
    {
        "source": "2026-05-27_architecture_cleanup.md",
        "title": "architecture_cleanup",
        "heading": "模型配置重复漂移",
        "distance": 0.28,
        "snippet": "这里记录了 ModelConfig 的统一入口...",
    }
]
```

保存位置：

- 第一版：放在 `result["memory_refs"]` 并展示在聊天结果
- 稳定版：写入 `tasks.metadata.memory_refs`

### 引用控制

第一版只展示，不提供交互。

第二版增加控制：

- “不使用历史笔记”
- “只使用上传笔记”
- “排除这条引用”
- 上传笔记去重/覆盖：同一文件重复上传时，应按文件路径或内容 hash 识别，避免重复写入向量库导致同一笔记被多次召回。

可通过自然语言先支持：

```text
只根据我上传的这篇笔记写，不要参考历史记忆
```

对应实现是在 intent 里增加：

```python
use_memory: bool = True
memory_mode: "auto" | "uploaded_only" | "disabled"
```

## 5.4 公众号偏好落地

### 当前基础

已有 `PreferenceLearner` 可以从评估数据学习：

- `preferred_length`
- `emoji_tendency`
- `paragraph_tendency`
- `tag_tendency`
- `strong_dimensions`
- `weak_dimensions`
- `strong_platforms`
- `weak_platforms`

但生成时主要消费：

- `preferred_tone`
- `favorite_platforms`
- `preferred_length`
- `custom_prompt`

### 目标能力

让偏好真正影响公众号文章：

```text
公众号默认读者：普通技术人
默认风格：通俗、具体、有个人经验
默认长度：1800-2500 字
弱项提醒：原创性、可读性
生成策略：开头先讲真实痛点，每节加例子，减少术语堆叠
```

### 偏好映射规则

| 偏好键 | 生成约束 |
|--------|----------|
| `preferred_length=long` | 公众号目标 1800-2500 字 |
| `preferred_length=medium` | 公众号目标 1200-1800 字 |
| `weak_dimensions` 包含 `readability` | 强制加入通俗解释、类比和例子 |
| `weak_dimensions` 包含 `originality` | 强制加入个人经历、项目细节、踩坑 |
| `weak_dimensions` 包含 `practicality` | 强制加入操作步骤和可复用建议 |
| `paragraph_tendency=long` | 保持章节完整，但段落不要过长 |
| `emoji_tendency=low` | 公众号正文少用 emoji |

### 建议新增公众号专属偏好

```text
gzh_target_reader: "普通技术人" | "小白读者" | "资深工程师"
gzh_default_style: "通俗科普" | "技术深度" | "经验复盘"
gzh_publish_goal: "涨粉" | "沉淀方法论" | "产品介绍" | "技术分享"
gzh_title_style: "痛点型" | "观点型" | "教程型"
```

这些偏好可以先通过命令或配置设置，后续再做 UI。

- 开始执行
- 不使用历史记忆

## 七、数据流设计

### 7.1 新生成任务

```text
用户消息 / 上传笔记
  ↓
IntentAnalyzer
  ↓
ConversationResolver 判断是否新任务
  ↓
MemoryManager:
  - 保存用户消息
  - 获取用户偏好
  - 检索相关笔记
  ↓
构建 Agent 输入：
  - 当前笔记
  - 写作要求
  - 公众号偏好
  - 引用笔记摘要
  ↓
Planner / Writer / Reviewer
  ↓
保存：
  - conversation_turns
  - tasks / drafts / edit_history
  - task_files
  - tasks.metadata.memory_refs
  ↓
UI 展示：
  - 生成内容
  - 下载按钮
  - 审核结果
  - 引用资料
```

### 7.2 修改上一版

```text
用户消息
  ↓
ConversationResolver 识别 revise_previous
  ↓
查找最近公众号结果：
  - 当前 session 中最近的 task/files
  - 或 tasks 中最近的 gongzhonghao draft
  ↓
构建修改输入：
  - 上一版公众号文章
  - 修改要求
  - 当前用户偏好
  ↓
生成新版本
  ↓
保存为新 task 或同 task 新 version
```

第一版建议保存为新 task，并在 metadata 中记录：

```json
{
  "parent_task_id": "task_20260531_001",
  "revision_instruction": "改得更通俗一点"
}
```

这样实现更简单，也便于历史追踪。

## 八、实施分期

### Phase 1：把记忆变成可见能力

目标：用户能看见历史和引用。

任务：

- 在生成结果中展示 `memory_refs`
- 将 `memory_refs` 写入 `tasks.metadata`
- 新增历史任务查询函数，优先列出公众号任务
- 在 UI 中增加“历史任务”区域
- 历史任务支持查看文件路径和最近评分

验收标准：

- 生成公众号文章后，可以看到本次引用了哪些笔记
- 重新打开页面后，可以看到最近任务
- 历史任务至少能展示标题、时间、评分、文件

### Phase 2：支持自然语言续写

目标：用户可以说“把刚才那篇继续改”。

任务：

- 新增 `ConversationResolver`
- 支持识别 `revise_previous`
- 能从最近任务中读取公众号 Markdown
- 修改请求生成新版本，并记录 `parent_task_id`

验收标准：

- 用户输入“把刚才那篇改得更通俗一点”可以正确修改上一版公众号文章
- 找不到上一版时给出清晰提示
- 新版本能下载，并能继续保存到公众号草稿箱

### Phase 3：公众号偏好生效

目标：系统越用越贴近用户风格。

当前进度：已完成第一版偏好注入。支持通过 `#!pref gzh_default_style 通俗科普`、`#!pref gzh_target_reader 普通技术人` 等命令设置公众号偏好；生成公众号文章时会把公众号专属偏好、长度偏好、弱项提醒映射为写作约束。页面左侧“当前默认”会读取真实偏好，设置偏好后自动刷新，生成结果中也会展示“本次应用的公众号偏好”。

任务：

- 增加公众号专属偏好键
- 将 `PreferenceLearner` 学到的弱项映射为写作约束
- 在生成结果中展示“已应用偏好”
- 增加 `#!prefs` 的可读化展示，区分显式偏好和推断偏好

验收标准：

- 设置 `gzh_default_style=通俗科普` 后，公众号生成稳定走通俗风格
- `weak_dimensions` 包含 readability 时，生成 prompt 会明确要求通俗解释
- 用户可以查看当前偏好，不再只有原始 key-value

### Phase 4：发布闭环稳定化

目标：公众号草稿箱不再是一次性按钮，而是任务状态的一部分。

任务：

- 保存公众号草稿箱发布结果
- 历史任务展示发布状态
- 发布失败时记录错误和重试入口
- 支持从历史任务重新发布到草稿箱

验收标准：

- 发布成功后历史任务显示“已保存草稿箱”
- 发布失败后能看到失败原因
- 不需要重新生成即可重试发布

---

## 九、风险与对策

| 风险 | 表现 | 对策 |
|------|------|------|
| 记忆污染 | 历史笔记误召回，导致文章跑题 | 展示引用来源，支持“只用上传笔记” |
| 上下文误判 | 用户想新写，系统误以为修改上一版 | 规则先保守，只有明显指代词才进入修改流程 |
| 数据关系混乱 | session、task、files、publish 状态分散 | 第一版统一在 tasks.metadata 补字段，稳定后再拆表 |
| UI 变复杂 | 历史、引用、审核、发布都挤在聊天页 | 默认折叠，只在生成后展示关键摘要 |
| 偏好过度影响 | 系统把所有文章写成同一种风格 | 用户当前指令优先级高于长期偏好 |

---

## 十、优先级建议

如果只做一个最小闭环，推荐顺序如下：

1. **引用透明**  
   成本低，立刻提升 RAG 可信度，也方便调试。

2. **历史任务中心第一版**  
   让生成结果不再丢在文件夹里，用户能找回。

3. **上下文续写**  
   这是 Agent 感最强的一步，能明显提升“好用”。

4. **公众号偏好落地**  
   让用户越用越顺手，但需要前面有稳定任务和评分数据。

5. **发布状态持久化**  
   放到最后，是因为它依赖历史任务中心。

## 十一、完成后的产品效果

完成后，用户体验应该从：

```text
我输入一段笔记，AI 生成一篇文章，然后我自己找文件、自己判断质量、自己发布。
```

变成：

```text
我把技术笔记交给 Content Agent，它会按我的公众号风格生成文章，
告诉我参考了哪些历史资料，给出质量审核结果，
我可以继续让它修改，也可以从历史任务里找回并保存到公众号草稿箱。
```

这才是“稳定好用”的关键：不是一次生成多惊艳，而是每次都能接住用户的真实工作流。
