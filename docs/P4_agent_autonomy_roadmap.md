# Content Agent → Autonomous Agent 路线图

> 算法: 保留 `main` 分支为工具版，在 `agent-autonomy` 分支上实现 Agent 化升级。

---

## 1. 现状诊断

### 当前是什么？
`content-agent` 当前是一个高级文案生成工具。

- 用户主动打开 UI → 粘贴笔记 → 点击生成 → 拿到文案 → 关闭
- 每次调用无状态，历史生成风格、用户反馈、发布数据均未被活用
- Orchestrator 的写-编循环虽然是"Agent 架构"，但对用户只是一个黑盒按钮背后的逻辑

### 什么是真正的 Agent？
Agent 与工具的核心区别：

| 维度 | 工具 | Agent |
|---|---|---|
| 触发 | 用户主动 | 自主感知环境，自主触发 |
| 决策 | 用户决定每一步 | Agent 自己规划路径 |
| 记忆 | 会话级/无状态 | 长期记忆，持续学习优化 |
| 目标 | 完成单次任务 | 追求一个长期目标 |
| 执行 | 用户点击后等待结果 | 定时/事件触发，循环执行 |

## 2. Agent 核心能力定义

目标：用户设定"本周发 3 篇小红书、2 篇公众号"，Agent 自己扫描笔记 → 生成 → 排期 → 发布，用户只审核。

### 2.1 感知（Perception）
- 监听 Obsidian Vault / 本地笔记目录，检测新增或修改的 `.md` 文件
- 监听 RSS/定向源，获取行业动态
- 监听已发布文案的数据回流（阅读量、点赞、转发）

### 2.2 决策（Decision）
- 自动判断笔记适合发哪些平台
- 自动选择最佳发布时间（根据平台活跃时段、历史数据）
- 自动排期，避免集中发布导致限流

### 2.3 记忆（Memory）
- 长期记忆：风格画像、高表现模式、平台限流规则
- 工作记忆：待发队列、已发文案、排期表
- 短期记忆：当前任务的中间状态

### 2.4 执行（Execution）（危险区，需审核门）
- 自动发布到公众号（待审核后发布）
- 自动发布到小红书（待审核后发布）
- 自动生成封面图并上传

## 3. 分阶段实施计划

### P0 — 感知 + 基础自动化（不需要审核门）

**3.1 Vault 监听自动触发**
- 定时扫描 `notes/` 目录，检测 `.md` 文件变化
- 新文件/修改文件自动加入"待生成队列"
- 通知用户（Feishu/Terminal）：检测到 N 篇新笔记，是否生成？

**3.2 定时任务排期**
- Cronjob 支持：定时扫描 → 生成 → 进入待发队列
- 排期策略：根据平台活跃时段自动分配发布时间
- 用户可设定目标："本周 3 篇小红书、2 篇公众号"，Agent 自己分配

**3.3 持久化状态存储**
- 用 SQLite 存储待发队列、已发文案、排期表
- 待发队列支持优先级、平台、计划发布时间
- 用户通过 UI 查看/管理队列

**3.4 风格画像持久化**
- 每次生成后，收集用户反馈（推荐/不推荐）
- FeedbackAgent 自动更新风格画像
- 历史数据持久化到 SQLite

### P1 — 数据回流 + 智能优化

**4.1 发布数据回流（手动导入）**
- 用户导入各平台后台数据（阅读、点赞、转发）
- Agent 分析高表现文案的共同特征
- 自动调整风格画像和策略

**4.2 自动选题**
- RSS 监听 + TopicPicker 自动生成选题建议
- 根据热点话题自动生成笔记草稿

**4.3 A/B 测试框架**
- 同一笔记生成多版本文案，自动分配到不同账号/时段
- 对比表现，自动优化

### P2 — 审核门 + 全自动发布（高风险）

**5.1 自动发布公众号**
- 接入微信公众平台 API（或 kuaifa CLI）
- 审核门：发布前强制用户审核（推送待审消息）
- 自动上传封面图、设置原创/转载

**5.2 自动发布小红书**
- 接入小红书创作者平台 API
- 审核门：同样强制审核

**5.3 错误恢复**
- 发布失败自动重试（限流、认证过期、网络问题）
- 审核被拒自动回退修改重发

## 5. 关键技术决策

| 决策点 | 方案 | 理由 |
|---|---|---|
| 定时触发 | Hermes Cronjob | 现有基础设施，无需新建 |
| 队列存储 | SQLite | 足够轻量，无需 Redis |
| 感知 | `watchdog` + 定时扫描 | 简单可靠，不强依 Obsidian 插件 |
| 通知 | Feishu/Terminal | 用户已有 Feishu 配置 |
| 审核门 | 强制人工审核 | 公众号/小红书发布不容失误 |
| 引擎 | ReAct 循环 + 状态机 | 复用现有 Orchestrator 模式，扩展即可 |

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 自动发布导致账号封禁 | P2 阶段必须加审核门，不允许无人审核发布 |
| LLM 生成异常内容被发出 | 敏感词检查强制执行 + 人工审核 |
| Vault 监听误触发 | 文件变化阈值 + 用户确认 |
| 排期失败/冲突 | SQLite 事务 + 唯一约束 |
| 数据丢失 | SQLite 定时备份 |

## 7. 首个可运行版本（MVP）

只做 P0 中的 Vault 监听 + 待发队列：

1. 用户设定 Vault 路径
2. Agent 每小时扫描一次
3. 新笔记自动生成三平台文案
4. 进入待发队列
5. 用户通过 Feishu/Terminal 看到通知："检测到 2 篇新笔记，已生成文案待发布"
6. 用户打开 UI 审核、调整、手动排期

这个 MVP 不需要接入任何平台 API，风险为 0，但已经体现了 Agent 的核心特征：自主触发、持久化状态、排期队列。
