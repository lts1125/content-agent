# Content Agent - 产品评审与进化路线图

> 基于当前 `dev/agent-enhancement` 分支的产品评审。项目已搭好“内容生成 Agent”的骨架（策略选择、计划执行、质量检查、多平台适配、配图渲染），但离真正可交付、可运营、可迭代的 Agent 产品还有距离。

---

## 一句话总结

> 当前是 **一个带 UI 的自动化内容生成脚本**，离真正的 Agent 还差：会记住用户的长期记忆、能在过程中暂停让用户做决策、能自动分析错误并调整策略、有数据库和 API 支撑多用户使用、内容发出去之后能回收数据反哺模型。

---

## ❌ L1 核心能力层：Agent 还缺“大脑皮层”

### 1. 记忆系统（Memory）— 目前几乎是空白

| 维度 | 现状 | 缺失 |
|------|------|------|
| 短期记忆 | `agent.history` 只保持当次会话聊天记录，进程重启消失 | 没有上下文窗口管理策略，长笔记可能直接撑爆 token |
| 长期记忆 | 无 | 用户偏好（习惯口语风还是专业风、常选哪些平台）没有持久化 | 
| 向量记忆（RAG） | 项目有 `test_rag.py` 但未集成到主流程 | 用户上传的笔记应该自动入库，后续生成时能语义检索引用 |

### 2. 真正的自主规划（Planning）— 还是“脚本执行”

| 维度 | 现状 | 缺失 |
|------|------|------|
| 动态任务分解 | `AutonomousPlanner` 是预设策略 + 固定步骤（搜索→生成→检查→保存） | 用户说“根据这篇笔记写公众号文章，再改写成 3 条小红书”，Agent 不会自己拆解成子任务 |
| 反思-修正循环 | LLMScorer 评分不合格后硬编码重试 3 次就放弃 | 不是“反思”，是硬编码重试。真正的反思应该是 Agent 自己分析“为什么这次分数低”，主动调整策略（换模型、换 prompt、换风格） |

### 3. 工具生态（Tool Use）— 工具太少，且用户不可见

| 维度 | 现状 | 缺失 |
|------|------|------|
| 工具种类 | search、browse、read、analyze、execute | 缺少图像生成（封面自动出图）、数据/代码执行、视频脚本工具 |
| 工具可见性 | chat_ui 里看不到 Agent 调用了什么工具、拿到了什么结果 | 工具调用过程应该可视化，用户才能信任 |

---

## ❌ L2 人机协作层：缺少“审核与反馈闭环”

### 4. 生成过程中的干预点 — 0 个

| 现状 | 缺失 |
|------|------|
| 用户输入需求 → 等进度条 → 看结果，中间完全不能干预 | 中途暂停：Agent 搜索完资料后，应该先问用户“我找到了这 3 篇参考资料，你觉得哪篇更贴合你的主题？” |
| | 分支选择：生成大纲后让用户选 A/B/C 方案，再进入正文写作 |

### 5. 明确的审核（Review）流程 UI

| 现状 | 缺失 |
|------|------|
| 质量检查是后台自动跑，用户只能看到最终分数 | 审核面板：展示每条规则检查结果（字数、敏感词、格式），让用户一键“采纳修改”或“忽略” |
| | 评分细项拆解：整体 85 分不够，要展示“结构 90、口语化 70、钩子 60”，让用户知道改哪里 |

### 6. 反馈闭环（Feedback Loop）

| 现状 | 缺失 |
|------|------|
| 用户下载完就走了，Agent 不知道“这次生成的好不好” | 显式反馈：生成结果旁加 👍/👎，收集用户对每篇文案的反馈 |
| | 隐式反馈：用户是否下载了、是否发布了、发布后有没有二次编辑 —这些数据应该回流到模型优化 |

---

## ❌ L3 基础设施层：离“生产级”差得远

### 7. 数据持久化 — 还是文件系统

| 现状 | 缺失 |
|------|------|
| 配置、历史、日历都存在 `~/.content_agent/` 的 json 文件里 | 数据库：SQLite/PostgreSQL 是底线，否则并发、查询、备份都是问题 |
| | 版本管理：用户修改文案后应该能看 diff、回滚到任意版本 |

### 8. 用户系统 — 单用户假设

| 现状 | 缺失 |
|------|------|
| 没有登录、没有权限、没有隔离 | 多租户支持（不同用户的历史记录不能串） |
| | 用量配额（免费用户每天 10 次，付费不限） |
| | 团队空间（一个团队共享素材库和模板） |

### 9. API 层 — 没有

| 现状 | 缺失 |
|------|------|
| 只有 CLI 和 Gradio Web UI | RESTful API，让第三方系统（CMS、企业微信机器人等）能调用 |

### 10. 可观测性（Observability）

| 现状 | 缺失 |
|------|------|
| 只有本地日志文件 | 链路追踪（LangSmith / Langfuse）：每次生成请求的完整调用链、耗时、token 消耗 |
| | 错误监控：Sentry 接入，线上报错实时告警 |
| | 指标看板：生成成功率、平均耗时、各平台评分分布 |

---

## ❌ L4 商业化/分发层：内容生产了，但分发没闭环

### 11. 多平台自动发布 — 只有公众号

| 现状 | 缺失 |
|------|------|
| 只有微信公众号草稿箱发布，依赖 kuaifa CLI | 小红书：没有接入小红书创作平台 API |
| | 抖音：没有接入抖音创作服务平台 |
| | 发布状态回查：发布后无法查询“是否审核通过、是否已上线” |

### 12. 数据回流 — 发出去就没了

| 现状 | 缺失 |
|------|------|
| 无 | 抓取已发布文章的阅读量、点赞、评论数 |
| | 根据表现数据反向优化生成策略（比如“带悬念钩子的标题点击率更高”） |

### 13. 模板与资产市场

| 现状 | 缺失 |
|------|------|
| 有 `template_presets.py`，但用户无法自定义和分享 | 用户保存自己的 prompt 模板 |
| | 模板市场（社区共享“爆款小红书模板”） |

---

## ⭐ 优先级建议

如果只能选一个方向开始，推荐按这个顺序补：

1. **记忆系统**（向量库 + 用户偏好） → 体验质变
2. **审核面板 + 中途干预** → 用户信任感
3. **数据库 + 用户系统** → 产品化的底线
4. **可观测性 + 反馈闭环** → 迭代优化的基础
